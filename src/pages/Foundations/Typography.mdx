## Core principle

Use typography to make information easier to understand, not more decorative.

Scientific interfaces often contain dense data, status information, technical
labels, long identifiers and changing values. Typography should help users see
what matters, compare values and act with confidence.

## Hierarchy

Use a clear and repeatable hierarchy across products.

- Use headings to structure the page.
- Use body text for explanation and supporting content.
- Use meta text for compact operational information and status.
- Use labels for controls, fields, table headers and short descriptors.
- Use mono type for technical values where alignment or precision matters.

Avoid creating one-off heading sizes or local typographic styles unless there is
a reusable reason.

Use heading levels in order where possible. Avoid jumping from `h1` to `h4`
unless the surrounding structure justifies it.

## Display and heading variants

Use display variants for large, high-level moments such as landing pages,
welcome screens, product introductions and documentation hero areas.

Use heading variants for application structure and content hierarchy. Display
variants should be used sparingly, and are not meant to replace the standard
heading hierarchy inside operational interfaces.

<Callout title="Under review">
  The current model uses dedicated display variants (`h1Display` to
  `h4Display`) for display typography, and `h1` to `h6` for application
  hierarchy. As the design system evolves, `h1` or `h2` may adopt the display
  typeface in some contexts. This decision is still under review and may change
  based on how applications and public-facing pages use them.
</Callout>

## Choosing a typeface

<Typography
  variant="h5"
  component="h3"
  sx={{ fontFamily: "var(--ds-font-family-default)", mt: 3.5, mb: 1 }}
>
  Inter
</Typography>

The default interface typeface. Use it for:

- Navigation
- Body text
- Buttons
- Forms
- Tables
- Dialogues
- Cards
- Labels
- Status messages

Inter should be the default choice unless there is a specific reason to use
Outfit or IBM Plex Mono.

<Typography
  variant="h5"
  component="h3"
  sx={{ fontFamily: "var(--ds-font-family-display)", mt: 3.5, mb: 1 }}
>
  Outfit
</Typography>

Used for display and high-level headings. Use it sparingly for:

- Product names
- Major page titles
- Welcome or landing areas
- Documentation hero headings

Do not use Outfit for dense application UI, tables, forms or technical values.

<Typography
  variant="h5"
  component="h3"
  sx={{ fontFamily: "var(--ds-font-family-mono)", mt: 3.5, mb: 1 }}
>
  IBM Plex Mono
</Typography>

Used for technical and aligned information. Use it for:

- Code
- Logs
- Console output
- Timestamps
- Numeric values where alignment helps comparison
- IDs (proposals, samples, beamlines)
- Numeric columns
- Technical table values
- File paths
- API-like values

Do not use mono type for general UI text.

## Technical values

Technical values should be easy to scan, compare and copy.

Use mono type where users need to inspect precise values:

```tsx
<Typography variant="mono1">
  energy=12.4 keV · exposure=0.5 s · frames=100
</Typography>
```

For tables with mixed content, use mono only for the technical cells rather than
the whole table.

## Truncation and overflow

Long technical values (paths, IDs, timestamps) can overflow a constrained layout
such as a table cell or a narrow panel.

Use `noWrap` inside a width-constrained container to cut the value to a single
line with an ellipsis, and pair it with a tooltip so the full value is still
available on hover or focus.

```tsx
<Box sx={{ maxWidth: 240 }}>
  <Tooltip title="/dls/i15-1/data/2026/cm12345-1/processed/sample_0042.nxs">
    <Typography variant="mono2" noWrap tabIndex={0}>
      /dls/i15-1/data/2026/cm12345-1/processed/sample_0042.nxs
    </Typography>
  </Tooltip>
</Box>
```

Don’t truncate a value without also giving users a way to read it in full.
Prefer a tooltip, or reflow the layout so the value has room to wrap.

## Numbers and units

Keep numbers and units readable.

```text
12.4 keV
0.5 s
180 ms
1,024 frames
```

Prefer a space between number and unit unless the notation convention says
otherwise. Avoid inconsistent formatting:

```text
12.4keV
0.5sec
180 milliseconds
1024 Frames
```

## Overlines and grouping

Overlines give lightweight hierarchy and grouping without introducing a full
heading. They are particularly useful in dense scientific interfaces, where more
structure is needed without adding visual weight.

Use overlines to:

- Group related controls
- Separate sections within cards or panels
- Label groups of settings
- Introduce collections of information
- Provide context above headings or values

```tsx
<Typography variant="overline">Acquisition</Typography>

<Typography variant="h4">Detector settings</Typography>
```

Prefer overlines when a full heading would add unnecessary visual weight.

## Logs and console output

Logs and console output should use mono type.

```tsx
<Typography component="pre" variant="mono1">
  [14:30:15] Starting data acquisition pipeline
  <br />
  [14:30:18] Detector initialised successfully
  <br />
  [14:30:22] Scan started — energy 12.4 keV, exposure 0.5 s
</Typography>
```

Use colour and status tokens carefully. Typography should not be the only way to
communicate severity.

## Light and dark behaviour

Typography should stay readable in both light and dark modes. Use semantic
foreground roles rather than raw colour values:

```tsx
<Typography color="text.primary">Primary text</Typography>

<Typography color="text.secondary">Secondary text</Typography>

<Typography color="text.disabled">Disabled text</Typography>
```

Avoid hard-coded greys for text. They may pass in one mode and fail in the
other.

## Accessibility

Typography must support legibility, contrast and a predictable reading order.

- Use sufficient contrast for text and icons.
- Do not use colour alone to communicate meaning.
- Keep line lengths comfortable for reading.
- Avoid very small text in dense operational areas.
- Preserve semantic headings where possible.
