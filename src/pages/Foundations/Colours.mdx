DiamondDS uses colour semantically. Colours are chosen for their purpose rather
than their appearance. Neutral colours provide structure and hierarchy, intent
colours communicate actions and status, and brand colours express Diamond
identity.

Most interfaces should be built mainly from neutral colours. Use semantic
colours deliberately, to draw attention to actions, changes in state, warnings,
errors or other important information. This keeps the interface clear, reduces
visual noise and makes meaningful information stand out when it matters.

Colour should support understanding, not carry meaning on its own. Also
communicate important information through text, icons, labels, layout or
interaction patterns.

## Colour principles

### Colour supports scientific work

Colour should help users understand information, state and action without
becoming visual noise. Scientific applications often show a lot of information
at once, so colour must be deliberate, predictable and accessible.

### Structure before meaning

Use neutral colours to build hierarchy, grouping and layout. Apply semantic
colours only when meaning needs to be communicated.

### Meaning before brand

Action and status colours communicate behaviour and system state. Brand colours
communicate Diamond identity, and should rarely be responsible for functional
meaning.

### Consistency over decoration

The same colour role should always communicate the same thing throughout the
system. Avoid using colour only to make an interface feel more decorative.

### Accessible by default

Colour must never be the only way something is communicated. Use labels, icons,
typography and spatial cues alongside it.

## Colour model

DiamondDS separates colour into three categories: **neutral**, **intent** and
**brand**. Keeping them apart means visual structure, operational meaning and
organisational identity stay distinct.

## Surface model

Neutral colours establish hierarchy and depth throughout the interface. Surface
roles define the relationship between areas of content, while elevation adds
visual prominence where it is needed.

In most Diamond applications, communicate hierarchy through surface roles,
spacing, borders and layout before relying on elevation.

### Read-only

Read-only content is available for inspection but cannot be edited.

Use read-only when users need to see information but must not change it. This is
common in scientific and operational workflows, where values may be locked,
generated by the system or controlled by permissions, but still need to be
reviewed, verified, compared, copied or referenced.

<Callout>
  Prefer **read-only** over **disabled** whenever users still need access to the
  underlying information. Use disabled mainly for unavailable actions and
  controls, not for data people need to read.
</Callout>

Disabled content may be left out of form submissions, skipped by keyboard
navigation, unavailable to some automation and testing tools, or out of reach of
integrations and data extraction. Read-only content stays part of the interface,
and stays available for inspection, copying, automation and accessibility
tooling.

Use read-only when users need to:

- Review values before making decisions.
- Compare settings or configuration.
- Copy text or data.
- Reference system-generated information.
- Access information that is currently locked for editing.

Read-only content should stay:

- Readable.
- Clearly identifiable as non-editable.
- Focusable where appropriate.
- Selectable and copyable where appropriate.
- Visually distinct from editable controls.

Read-only content should not look disabled. Disabled content says a control is
unavailable. Read-only content says a value is available but cannot be changed.

### State priority

When more than one state applies, use this order.

```text
Disabled
  ↓
Error
  ↓
Selected
  ↓
Active
  ↓
Hover
  ↓
Rest
```

Disabled and error states always win over other visual states.

Scientific interfaces often contain:

- Large tables
- Live data
- Monitoring views
- Control panels
- Acquisition screens

In these environments, colour must keep a strong signal-to-noise ratio.

## Accessibility

Colour plays an important part in accessibility, but should not be the only way
something is communicated. Combine colour with text, icons, labels, layout and
interaction patterns.

- Do not communicate meaning through colour alone.
- Make sure important states stay distinguishable in both light and dark modes.
- Pair status colours with labels, icons or supporting text.
- Use semantic colour tokens rather than hardcoded values.
- Test colour usage in realistic workflows and data-dense interfaces.

For contrast requirements, focus indicators and broader accessibility standards,
see [Accessibility](/standards/accessibility).

## Token reference

The token reference connects DiamondDS semantic colour roles to CSS variables
and MUI palette roles. Use semantic tokens and MUI palette roles in components,
and avoid hardcoded hex values.

`[token]` stands for a role such as `primary` or `danger`, and `[role]` for its
